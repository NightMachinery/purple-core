# Playlists core model, local operations, policy decisions, and diff notices (format 1)

This document specifies the first five A1 slices in `purple/purple_playlists.h`, `purple/purple_playlists.cpp`, `purple/purple_playlists_ops.h`, `purple/purple_playlists_ops.cpp`, `purple/purple_playlists_policy.h`, `purple/purple_playlists_policy.cpp`, `purple/purple_playlists_diff.h`, and `purple/purple_playlists_diff.cpp`, together with the opt-in JSON size-budget extension in `purple/purple_sync_json.h`.

## Scope of these slices

The model slice implements in-memory data structures, strict format 1 JSON parsing and validation, canonical JSON serialization, and pure register-level `JoinPlaylistLibraries` and `PlaylistLibraryContains` operations.

The local operations slice builds on that model with deterministic playlist ID formatting, local create/rename/delete/restore/purge/add/relink/remove/reorder editing, structured undo records and undo application, per-playlist monotonic `2^52` stamp allocation, the 24 MiB local edit size guard, and playlist/song display ordering.

The policy slice adds pure song qualification, shared metadata preparation, pinned-selection chat order sorting, and gated automatic-purge decisions over an already-merged library.

These slices perform no file I/O, compression, network transport, clock reads, `AccountFiles` wiring, settings parsing, or UI integration.

## Shared JSON budget contract

`CanonicalizeSyncJson(json)` keeps its original one-argument signature and 4 MiB cap for settings and sync-state callers. A new opt-in overload `CanonicalizeSyncJson(json, maximumBytes)` accepts an optional byte budget so local playlist files (`library.json`) can be parsed uncapped (`std::nullopt`) while still reusing the same strict RFC 8785 lexical, UTF-8, surrogate, integer, duplicate-key, and depth checks.

## Format 1 data model and validation

A `PlaylistLibrary` holds `format` (exact integer `1`), `playlists` keyed by playlist ID, and a `purged` set of permanently deleted playlist IDs.

- **Format version:** `format` must be integer `1`. Any larger integer reports `NewerFormat` immediately before checking format-1 keys; anything else is `Invalid`.
- **Playlist IDs:** `pl-` followed by 16 lowercase RFC 4648 base32 characters (`[a-z2-7]`).
- **Purged set:** In JSON, `"purged"` maps playlist IDs to `1`. No purged ID may appear in `"playlists"`.
- **Playlists and partial records:** Each playlist holds optional registers `title`, `deleted`, `order`, and `songs`. At least one of the four must be present; an empty playlist object is invalid. Absent registers stay absent across parse and serialize round-trips, and act as the bottom element during merge.
- **Registers and stamps:** Every register is a `[value, stamp]` pair where `stamp` is an integer in `[1, 2^52]`.
- **Playlist title:** Valid Unicode, 1 to 64 code points, trimmed, single-line, with no C0/C1 control characters or Unicode line/paragraph separators.
- **Order list:** An array of distinct unsigned decimal document ID strings (`1` to `2^64 - 1`, no leading zeroes). Order lists may reference document IDs absent from `songs`.
- **Songs map:** Maps unsigned decimal document ID strings (`1` to `2^64 - 1`, no leading zeroes) to registers whose value is either `false` (removal tombstone) or a source object. A boolean `true` song value is invalid.
- **Source object:** Requires `peer`, `msg` (`1` to `2^31 - 1`), `meta` (`title`, `perf` of 0 to 96 valid Unicode code points each, and `dur` in `[0, 2^31 - 1]`), and `since` (`1` to `2^52`, with `since <= registerStamp`). Optional `un` is 4 to 32 characters of `[A-Za-z0-9_]`. Optional `alt` holds 1 to 3 fallback entries (`peer`, `msg`, optional `un`) when present in JSON, and is omitted when empty. Every `alt` entry must differ in normalized `(peer, msg)` from the primary source and from all other `alt` entries.
- **Peer normalization and privacy:** Peer tokens reuse `Purple::ParsePeerToken` and `Purple::PeerTokenText` with a caller-supplied `selfUserId`. Any `user:<selfUserId>` token normalizes to `self`, so the account's numeric user ID is never serialized. Access hashes, file references, and local paths are never part of the format.
- **Unknown keys:** Any unknown key at the root, playlist, source, metadata, or fallback level makes a format-1 document `Invalid`.

## Canonical serialization, join, and contains

`SerializePlaylistLibrary` validates the library, normalizes peer tokens against `selfUserId`, and emits compact UTF-8 canonical JSON with object keys sorted by UTF-16 code units (including sorting decimal document ID keys in `songs` lexicographically, so `"10"` precedes `"2"`) and RFC 8785 string escaping.

`JoinPlaylistLibraries(a, b, selfUserId)` merges two valid format-1 libraries without creating or modifying stamps:

- `purged` is the union of both purged sets, and any purged ID is dropped from `playlists`.
- Absent registers act as bottom (`join(absent, x) = x`).
- Present registers keep the pair with the larger stamp. On equal stamps, the pair with the larger canonical JSON value bytes (compared as unsigned UTF-8 byte sequences) wins, so a song source beats `false` and `deleted = true` beats `deleted = false`.
- `PlaylistLibraryContains(outer, inner, selfUserId)` holds iff `SerializePlaylistLibrary(JoinPlaylistLibraries(outer, inner))` equals `SerializePlaylistLibrary(outer)` byte for byte.

## Local operations, undo, and display order

`purple/purple_playlists_ops.h` and `purple/purple_playlists_ops.cpp` implement pure value-returning local mutations over `PlaylistLibrary`:

- **Playlist IDs from entropy:** `FormatPlaylistId` encodes 10 caller-supplied entropy bytes into `pl-` plus 16 lowercase RFC 4648 base32 characters. `CreatePlaylist` refuses collisions against either active `playlists` or `purged`.
- **Stamps and batching:** Stamped edits allocate `stamp = max(nowMs, playlistMaxStamp + 1)`. Batch operations (`AddPlaylistSongs`) reserve a contiguous span `s .. s + writeCount - 1` up front and fail atomically with `StampOverflow` if `s + writeCount - 1 > 2^52`.
- **Lifecycle edits and guards:** Mutation targets must have both title and deleted registers (`PlaylistIncomplete` otherwise). Rename, Add, Remove and Reorder refuse deleted playlists (`PlaylistDeleted`); Delete on an already deleted playlist and Restore on an active playlist are no-ops. All mutations return `changed = false` without allocating a stamp or undo entry on idempotent no-ops (same title, already deleted, already active, unchanged `order`, or songs already active at the same normalized `(peer, msg)`).
- **Adding, relinking, removing, and reordering songs:** `AddPlaylistSongs` rejects duplicate `documentId` inputs within one call, preserves input order via consecutive stamps on new or relinked songs, ignores unchanged already-active songs without overwriting `meta` or `since`, and relinks active songs with a changed normalized `(peer, msg)` by keeping `since`, taking the incoming primary source and metadata, and prepending the old primary and distinct `alt` entries up to 3 fallbacks. `RemovePlaylistSongs` tombstones only active songs. `ReorderPlaylistSongs` writes the full active `order` register only when the input is an exact permutation of currently active document IDs.
- **24 MiB local edit cap:** Edits that modify the library enforce a 24 MiB canonical JSON budget (`LibraryFull`). If an already oversized merged library (> 24 MiB) is passed in, mutations whose canonical JSON is strictly smaller than the input size (such as tombstoning songs or `DeleteForeverPlaylist`) remain permitted so users can free space.
- **Undo records and conflicts:** `CreatePlaylist` returns a `Create` undo record; `UndoPlaylistOperation` permanently purges the playlist ID only if the playlist is still untouched since creation, and returns `UndoConflict` otherwise (so merged remote activity or subsequent edits are never silently purged). `CopyPlaylist` returns a `Copy` undo record capturing the exact expected post-copy playlist snapshot; `UndoPlaylistOperation` normalizes peer IDs against `selfUserId` and permanently purges the copy only if the live playlist still matches that snapshot verbatim (refusing with `UndoConflict` after any post-copy rename, membership edit, reorder, deletion, or merged stamp bump). Register-level edits return prior `title`, `deleted`, `order`, and affected `priorSongs` (`std::nullopt` for newly added songs so undo writes a removal tombstone) and replay only those captured registers using fresh monotonic stamps. Undoing a reorder whose prior order register was absent writes a fresh empty order register, so the undo survives merging the old reorder. Reorder checks the effective visible sequence as well as the stored list before declaring a no-op, because a re-added song can move to the end while the stored list stays unchanged. Non-delete undo writes fail with `PlaylistDeleted` if the playlist is currently deleted. `DeleteForeverPlaylist` has no undo and can proceed at stamp `2^52`.
- **Copying playlists (`CopyPlaylist`):** Validates the destination library, entropy, `nowMs`, and the `source` playlist itself (including deleted, detached, purged-ID, or `2^52`-saturated sources as long as `title` and `deleted` registers are present and structurally valid). Formats `<old> (copy)` by truncating `<old>` to at most 57 Unicode code points without splitting UTF-16 surrogate pairs before appending `" (copy)"` so the copy stays within the 64-code-point trimmed single-line limit. Copies only visible songs in `PlaylistVisibleSongIds(source)` display order into a fresh active playlist (`order` cleared, `title`/`deleted`/`order` stamped `nowMs`, songs stamped `nowMs + 1 .. nowMs + N`), preserving `selfUserId`-normalized `peer` and up to three `alt` fallbacks while checking the `2^52` stamp span atomically and enforcing the 24 MiB local edit cap once on the resulting library.
- **Display ordering:** `PlaylistVisibleSongIds` emits active songs in `order` where `song.since <= order.stamp` (Group 1), followed by remaining active songs ordered by ascending `since` and numeric `documentId` (Group 2). `ListVisiblePlaylists` filters out deleted and incomplete playlists and sorts by descending caller-supplied `recentUseMs`, then case-insensitive title (`Qt::CaseInsensitive`), then ascending playlist ID.

## Policy decisions and gated automatic purge

`purple/purple_playlists_policy.h` and `purple/purple_playlists_policy.cpp` implement pure qualification, metadata normalization, chat-order sorting, and `AutoPurgePlaylists`:

- **Song qualification (`QualifySong`):** Validates nonzero `documentId` and positive `messageId`, an audio attribute without the voice flag, a regular server message as main message media (never inferred from `hasAudioAttribute`), and explicit exclusions defaulting false for positive capabilities (`isRegularServerMessage`, `isMainMessageMedia`, `hasAudioAttribute`) and false for exclusions (`isScheduled`, `isLocalUnsent`, `isSponsored`, `isStory`, `isProfileMusic`, `isSecretChat`, `isRichMediaSubtrack`, `hasSelfDestructTimer`). Protected-chat or protected-message songs pass only when `protectedContentAllowed` is true; unprotected songs are unaffected, and existing playlist entries are never mutated when policy changes.
- **Metadata preparation (`PrepareSongMeta`):** Falls back to `fileName` only when raw audio `title` is empty, validates all Unicode code points across `title` and `performer` against unpaired surrogates before truncating each to 96 code points without splitting surrogate pairs, enforces duration in `[0, 2^31 - 1]`, and checks the resulting fields with `IsValidPlaylistMetaText`.
- **Pinned chat order (`SortPlaylistChatOrder`):** Validates nonzero `documentId` and positive `messageId`, places items from a migrated-from basic group before current-chat items, and orders within each group by ascending `messageId` then ascending `documentId`.
- **Automatic purge (`AutoPurgePlaylists`):** Evaluates an already-merged library without touching disk, clock, or network, allocating no stamps, producing no undo entries, and imposing no 24 MiB edit size cap. Invalid or `NewerFormat` local libraries return all input state unchanged. Blocking facts default false and sync defaults enabled, so partial context fails closed and the sync-off exception requires an explicit choice. A playlist is due when `deleted` is `true` and `nowMs >= deletionStamp + 30 days` (computed overflow-safely), including valid partial playlists whose winning `deleted` register is present. Non-purged playlists, registers, and stamps stay bit-for-bit intact.
- **Sync-state gating and `dueSeen` retention:** When `syncEnabled` is false, only `serverRequestSucceeded` in the current step is required, and due playlists purge immediately. When `syncEnabled` is true, purge requires `serverRequestSucceeded`, complete discovery (paged to end, missing memo items resolved, all candidates classified/read without transient read failure or unknown ownership, and any vanished memo record paired with at least one new valid record), `noPresentNewerFormatRecord`, and a matching `dueSeen` record (`deletionStamp` and `firstSeenAtMs`) observed at least 15 minutes earlier. That deletion must already have been 30 days old at `firstSeenAtMs`; impossible earlier observations are replaced with a fresh observation. Incomplete or unvalidated steps leave `dueSeen` unchanged so failed steps never start or shorten the wait, and clock rewinds (`nowMs < firstSeenAtMs`) keep the earlier `firstSeenAtMs` without wrapping or purging early. On an otherwise complete clock-validated step, no-longer-due, absent, restored, or changed-stamp deletions are cleared/reset. When a newer-format record is present during complete discovery, no purge runs and `dueSeen` is cleared conservatively so unreadable newer-format state cannot keep an earlier observation alive across format barriers; once no newer-format record remains, a fresh 15-minute observation starts.

`purple/purple_playlists_diff.h` and `purple/purple_playlists_diff.cpp` implement pure `DiffPlaylistLibraries(before, after, selfUserId)` comparisons between two in-memory `PlaylistLibrary` snapshots:

- **Validation and purity:** Validates `selfUserId` and both `before` and `after` via `ValidatePlaylistLibrary`, refusing invalid or `NewerFormat` inputs with `side` (`SelfUserId`, `Before`, or `After`) and zero partial changes, register diffs, or notices. Never mutates inputs, never allocates stamps or touches clock/RNG/disk, and imposes no 24 MiB size limit so oversized merged libraries compare in `O(N log N)` time without canonical serialization.
- **Content/display diffs vs stored registers:** Emits deterministic `PlaylistDiffEntry` records sorted lexicographically by playlist ID and numerically by document ID, tracking before/after `PlaylistDiffPresence` (`Absent`, `Visible`, `Deleted`, `Incomplete`, `Purged`), real title/deleted value changes, effective `PlaylistVisibleSongIds` display-order changes (including order-stamp or `since` changes that alter display order), added/removed active song IDs independent of playlist `deleted` state (deleting a playlist never marks contained songs removed), and changed source values (`primarySourceChanged`, `primaryUsernameChanged`, `fallbacksChanged`, `metaChanged`, `sinceChanged`) normalized with `PeerToken` self semantics. Relinking counts changes to `(peer, msg)` only; updating the username lookup hint is a separate value change. Pure register-stamp increases, `self` token roundtrips, orphan `order` IDs that leave display order unchanged, and absent-vs-tombstone song states do not trigger content changes or summary counts and are reported separately in `registerChanges`.
- **Hidden-playlist notices:** Emits at most one `PlaylistNotice` per playlist ID only when the playlist was `Visible` in `before` (`title` and `deleted == false`, not purged) and `after` explicitly marks it `Purged` (`PurgedElsewhere` -> `KeepCopy`) or `deleted == true` even inside an otherwise incomplete record (`DeletedElsewhere` -> `Restore`), with `Purged` winning classification. Each notice preserves the complete normalized pre-merge `Playlist` snapshot (title, `deleted == false`, `order`, `songs`, original stamps, normalized primary and up to 3 fallbacks, and metadata) compatible with `CopyPlaylist`. No notice is emitted for renames, reorders, song edits, new playlists, prior-deleted purges (including automatic purges of `Recently deleted`), already-incomplete playlists, or simple absence/incompleteness without an explicit deleted or purged fact.
